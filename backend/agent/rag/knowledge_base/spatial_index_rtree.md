# 空间索引：R-tree（STRtree）为什么比线性扫描快

对应本项目 `geo_data.SpatialIndex` 的两种后端，以及
`agent/spatial_index/benchmark.py` 里的真实对比实验。

## 线性扫描的复杂度

最朴素的做法：查询一个点附近的POI时，遍历数据集里的每一个点，算一次距离，
再排序取前K个或过滤半径内的。时间复杂度是 O(N)（N=数据集大小），排序另加
O(K log K) 或 O(N log N)。当 N 很小（本项目原始数据91个点位）时，O(N) 本身
就是几十次浮点运算，现代CPU下不到1毫秒，线性扫描完全够用——这也是为什么
项目最初直接用线性扫描没有问题。

## R-tree 系列索引的核心思想

R-tree（以及本项目实际使用的变体 STRtree，Sort-Tile-Recursive R-tree）
是一种层次化的空间索引：把点/图形按空间位置分组，用外接矩形（bounding box）
逐层打包成树状结构。查询时先看根节点的几个大矩形跟查询范围有没有交集，
没交集的整个子树直接跳过，不需要遍历子树内的每一个点。

- 平均查询复杂度约 O(log N)（最坏情况下退化到接近 O(N)，取决于数据分布
  和树的构建质量，STRtree 通过预排序打包让树相对平衡，最坏情况出现概率低）；
- 代价是需要预先构建索引（一次性 O(N log N)），之后每次查询才能享受
  O(log N) 的收益——如果只查询一次，构建成本可能反而不划算，这也是为什么
  索引更适合"数据相对静态、查询频繁"的场景。

## 什么时候值得从线性扫描换成R-tree

不是"R-tree永远更快"，而是要看数据规模和查询频率：

- 数据规模小（几十到几百个点）、查询也不频繁：线性扫描的常数开销很小，
  两者实际耗时差距在实践中可能不明显，甚至线性扫描因为没有索引构建/树遍历
  的额外开销，在极小数据集上可能更快；
- 数据规模变大（几千到几万个点）：线性扫描的O(N)开销线性增长，R-tree的
  O(log N)增长曲线明显更平缓，差距会随数据量拉开；
- 具体的数量级拐点在哪里、实际提速多少倍，不能凭直觉估计，需要实测——
  这正是本项目在 `spatial_index/benchmark.py` 里做的事：把数据规模从91个
  点位一路扩展到上万个模拟点，分别记录两种后端的真实查询耗时，用数据说话，
  而不是默认"数据结构升级就一定更好"。

## 本项目的实际选择

`SpatialIndex` 同时保留两种后端（`backend="linear"` 和 `backend="rtree"`），
默认使用 STRtree，但查询接口完全一致，方便随时切换对比。这也是为什么用
Shapely 的 STRtree 而不是单独的 `rtree` 包——STRtree 不依赖额外的系统库
（`rtree` 包底层依赖 libspatialindex C库），部署更简单，且性能特性接近。
